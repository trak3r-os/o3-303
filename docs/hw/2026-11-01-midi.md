# Unit session 2026-11-01: MIDI over USB, with numbers (MD1)

The tool is `tools/midi_check.py`. A computer on the unit's USB port is the other end of the unit's MIDI: it listens to the unit's USB
audio, reads its console, and every phase prints PASS or FAIL with a measured number against a limit. The maintainer's ask (2026-11-01): the
MIDI on the unit has to be rock solid, with numbers. The manual says "not yet checked on a unit" (section 10). This session is that check
for everything the USB cable can carry. **DIN is owed** (below).

**State:**
- **Run by hand on the unit** on 2026-11-01, with small scripts that came before the tool and cover the same phases (o3-303-d1, between SU1p's rows). The numbers are in "Results".
- **The tool itself:** only its self-test against a fake unit has run (ctest `midi_check_selftest`). Its first run on a unit is checklist rows 1 to 7, still open.

## What it needs

- The unit on USB, with the image running; `ls /dev/serial/by-id/*Track3r*` (the console) and `amidi -l` (the MIDI node, `Track3r MIDI`; the tool's
  default is `/dev/snd/midiC1D0`, `--midi-dev` says another) and `arecord -l` (the capture device, found by name; `--audio-device hw:C,D`).
- The USB audio profile P8 (the default at boot: the master is on capture channels 7-8). The `state` line says `usb=P8`.
- Nothing else using the unit's console, MIDI node or capture stream: **the unit is shared with track3r-os test sessions. Ask first, note the start
  state, never open `/dev/ttyACM0` by hand during a run.** `lsof` on the three devices shows who has them.
- AUTOSAVE OFF in Config (303) if the maintainer cares about the patch: the learn phase moves the cutoff and ends with a `reset` that drops it.
- `--learn-baseline none` only after the maintainer or the tester has looked at Config's MIDI page: CLEAR LEARN says `0 BOUND`. The console
  shows no binding count, and CLEAR LEARN erases every binding, so the learn phase runs only on that word.
- No card writes beyond the kit's settings file (`Apps/o3_303/system.o3s`, written by the Config rows within about 1.5 s of a change and by
  the learn phase's bindings). No firmware is installed by this page; it needs the image already on the unit, by the documented path.

## How the tool keeps the unit safe

1. It opens the console and sends `version`. If the text does not contain `--expect-version` it prints `REFUSED`, sends nothing else and exits 2. Then
   `state` must say `app=O3-303`. Only then are the MIDI node and the audio device opened.
2. It records the start state (the eight MIDI rows of Config, the screen, whether Config is open, the transport, the tempo) in
   `DIR/start_state.json`, plus `baseline/` (`version`, `state`, `log`, `midi`, `cpu`, `crash`). It stops if the unit already follows a clock.
3. It sends only `version state midi cpu crash log key enc leds usb reset` (`reset` only in the learn phase). `console_transcript.txt` has every line.
4. In a `finally` block it stops the senders, waits for the unit to let a clock go, stops the transport, puts the eight rows back one at a time
   (read back through `midi` after each key; the hidden FOLLOW PORT too), puts the own tempo back on MASTER, goes back to the screen found, and
   prints the end state next to the start state. Each item is a PASS or FAIL check of its own. Exit 4 means the unit was not fully put back.
5. A run that died hard (power, `kill -9`, the USB cable) leaves `start_state.json`: `tools/midi_check.py --restore-from DIR --expect-version TEXT`.

## Commands

```sh
V='<the label of the image on the unit>'
D=/tmp/midi-check-1        # a directory on the computer, not on the card
tools/midi_check.py --expect-version "$V" --out $D --learn-baseline none                   # all phases, in order, restore always
tools/midi_check.py --expect-version "$V" --out $D --phases identity,notes                 # one phase (identity always runs first, restore always last)
tools/midi_check.py --expect-version "$V" --out $D --phases follow --follow-tests start,profile
tools/midi_check.py --expect-version "$V" --out $D --phases soak --soak-seconds 600        # a shorter soak
tools/midi_check.py --expect-version "$V" --out $D --no-audio                              # no capture: the audio checks say "not run" and the run ends 3
```

Exit status: 0 all selected phases passed, 1 a check failed, 2 refused, 3 nothing failed but a check could not run, 4 the unit was not restored.

## The phases, their limits and what each proves

The limits are constants at the top of `tools/midi_check.py`, each with its reason. They are proposals written before the first run; the ones
marked (calibrate) are for this session to settle with the first numbers, and the settled value goes into the tool, not into this page.

| Phase | What it does | Limits (constant) | What a PASS proves |
|---|---|---|---|
| **identity** (a few s) | `version` and `app`; the five baseline reads; the MIDI config found | `version` contains the text, `app=O3-303`, not following; a `crash` record found at the start is saved and every later check requires it unchanged | The tool is talking to the image it was told, from a known state |
| **notes** (about 1.5 min) | Notes on the user's channel (IN CHANNEL, or 1 on OMNI): five pitched notes, velocity 0 as a note-off, CC 123 and CC 120 on a held note, 200 overlapping notes with their offs shuffled. The counters from `midi`, and the capture of channels 7-8 | `messages` +1 per message, `dropped` +0, RMS while held at least -50 dBFS (calibrate), silence before and within 5 s after the last off (-60 dBFS), pitch within 20 cents by autocorrelation (C2 G2 C3 G3 C4), no stuck note after the burst | A note-on makes sound at the right pitch, every kind of note-off ends it, nothing hangs, nothing is lost |
| **follow** (about 15 min) | The computer is the clock master (a thread, `perf_counter_ns`, the last millisecond busy-waited; its lateness is printed). FOLLOW CLOCK on, FOLLOW PORT USB, TRANSPORT IN on, CLOCK OUT on. Start then 120 BPM; 60, 90, 120, 140, 174, 200 and 300 BPM; +-2 ms jitter at 128 BPM; tempo steps; a 100 to 140 BPM ramp; a 12-clock dropout and 3 s of silence; Stop, Continue and Song Position Pointer; a 10-minute run counting the clocks out against the clocks sent | Lock within 48 clocks, tempo mean within 0.1 BPM and any readout within 0.3 (calibrate), jitter: within 0.5 BPM and never unlocked, step reacquired within 3 s (calibrate), ramp mean error 1.5 BPM and worst 3 (calibrate), release 48 clocks after the last clock (+0.75 s), the tempo held until then, Stop and Continue within a beat, long run: clocks out against clocks sent within 1 at the end and 3 while running, phase offset drift under 1 ms and its scatter under 1 ms | The unit follows a USB clock accurately and keeps it through jitter, steps, a gap and ten minutes, and what it sends out is what came in (no slip) |
| **clockout** (about 3 min) | FOLLOW off, CLOCK OUT and TRANSPORT OUT on, the unit's tempo set to 120 and 174 BPM on MASTER (the tool reads it back), Play for 60 s each, the clocks read on the raw node | Mean error under 0.02 % (widened only on a short run, by the 3 ms edges), interval stdev under 0.6 ms (the 1 ms USB frame gives 0.41 ms at best: that is the floor), worst interval within 2 ms, no missing or extra clock, the count against what the unit counted within 1, one FA before the first clock, one FC on Stop and no clock after it | The unit is a good clock master over USB; its Start and Stop come in the right order |
| **learn** (about 2 min, needs audio) | INSTRUMENT VOICE, Shift + F1 (CUTOFF), CC 74: the brightness of a held note at CC 127, 0, 64, 127, 0 before a binding (negative control), after it, after a `reset`, and after CLEAR LEARN. The console has no binding count and no parameter readout, so the sound is the witness | Control spread at most 3 dB, 127 brighter than 0 by at least 6 dB (calibrate), 64 in between by 1 dB, repeats within 3 dB, the binding survives `reset`, CLEAR LEARN frees the controller. Ends with CLEAR LEARN and a `reset` that drops the moved cutoff | Learn binds, moves the parameter with pickup, is saved, and clears |
| **stress** (about 2.5 min) | 1,000 CC a second for 30 s on 10 controllers and 4 channels; 2,000 notes in 2 s (pairs, then 2,000 note-ons held and their offs shuffled); ten 1 KB SysEx blobs in 16-byte writes with clocks and notes between the writes; a clock byte inside 1,000 running control changes; IN CHANNEL 3 with notes on the other 15 channels | Per part: `messages` equal to what was sent, `dropped` 0 (storms: reported, a full ring drops and counts by design), `usb bytes-in` equal to the bytes written, no overrun or discard, `cpu` underrun, mute, late, slips, hwfault and over-budget unchanged, render peak at most 75 %, `crash` empty, the voice silent at the end; the clock stays locked through SysEx and through clock bytes in messages; other channels silent | Floods and storms cost no message, no stuck note and no crash; realtime bytes inside messages are handled; the channel filter works |
| **soak** (31 min) | Clock in at 128 BPM, a 16th-note pattern, CC 74 on a 60 s sine; `midi`, `cpu`, `crash` every 60 s | `crash` empty throughout, `dropped` 0, din and usb errors 0, overruns and underruns 0, render peak at most 75 %, reacquires only in the first minute, locked 99.9 % of readouts, tempo within 0.3 BPM, clocks out against clocks sent within 1, the voice answers after | Nothing degrades over half an hour |
| **restore** (always) | As in "How the tool keeps the unit safe" | Every Config row, the screen, the transport, the tempo and the follow state equal to the start | The unit is as it was found |

How a realtime byte reaches the unit: ALSA gives a realtime byte (F8, FA to FF) its own USB-MIDI packet even inside a running message, so over
USB the unit never sees one in the middle of a message. What the tool can prove over USB is that the packets arrive in order and the messages
stay whole; the parser's mid-message case is DIN's, and owed.

## How long

Identity and notes about 2 minutes, follow about 15 (the 10-minute long run is the bulk), clockout 3, learn 2, stress 2.5, soak 31, restore half a
minute: about 56 minutes. These are the sums of the tool's own waits, to be replaced by the first run's wall clock. A first session can run
`--phases identity,notes,clockout` (about 6 minutes) before the long ones. `--quick` scales every duration down (about 10 minutes) for a smoke run;
its numbers are not a proof.

## Owed

- **DIN.** No DIN interface on the computer: the DIN ports, their parser (realtime bytes inside a running message, running status) and the 31,250
  baud timing are unproven. It needs a loopback cable from the unit's MIDI OUT to its MIDI IN and a hand, and then the same counters.
- **The binding itself** has no console readout; the learn phase proves it by sound. A readout of the bindings and of the parameter would let the
  check say more (a follow-up in the kit, not in this tool).

During the window the unit's log showed `pads: scanner not answering`. That is the pad bus, not MIDI, and at the hand-back the log read `pads: scanner answers`.

**Findings.**
1. **Cold start, o3-sdk's own code** (`platform/mk66/midi/src/midi_service.cpp`, `manage_follow`):
   - The loop attaches only once it has two clocks, with a fixed 120 BPM nominal period until then.
   - So a Start that comes with the master's first clock begins one clock period late, and the position then catches up at the +25 % slew.
   - track3r-os attaches on a Start as soon as the loop has one clock.
   - Fix: lane MC1 in o3-sdk, then the re-test: a cold start at 60, 128 and 200 BPM, where the first clock out should be within about 2 ms of the first clock in.
2. **A SysEx flood can cut channel messages: a track3r-os item, ported code kept identical** (`platform/mk66/midi/src/usb_bind.cpp`):
   - `usb_midi_from_host` pushes every byte of every USB-MIDI event into the 256-item in-ring, SysEx bytes too, and a full ring drops single bytes.
   - The suggested fix (track3r-os first, then the port): drop SysEx before the ring and push each channel message whole or not at all.
3. **The lock flag under jitter: a track3r-os item** (the ported clock loop's 5 % threshold). Cosmetic: the tempo holds.
