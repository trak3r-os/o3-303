# Unit session 2026-10-26: M3b-a (the sequencer engine and the beat freeze) over USB

The remote test session ran it with `o3console.py` and `o3audio.py`, the way o3-sdk `docs/hw/2026-10-25-usb.md` describes. The unit is shared with track3r-os's own test sessions, so the round started from the state it found and ended on that same state.

## Results

| Check | Result |
|---|---|
| Install by `--put` / `--update` | ok, about 15 s; `version` = `f3c08e6bca2a / o3sdk 5d58f6bb1117`; no blink code, `crash` empty |
| Render CPU, idle (not playing) | mean about 35.5 % of a block (3 samples over 30 s), max 39.7 % |
| Render CPU, playing | mean about 37 % (4 samples over 60 s), since-boot max 44.4 %, reached in plain play before any freeze; 0 underrun, 0 fault |
| Render CPU, freeze held | not measurably above plain play: 10 samples each over 20 s, 36.2 % not held against 35.2 % held (the difference is block-to-block jitter); the max was 113,859 cycles (43.6 %) both held and not held, so the freeze never set a new peak |
| Playback against the 2026-10-25 o3_303 | same screen and pattern; channel 7 at -1.4 dBFS peak, -11.6 dB RMS, as before; channels 1-6 silent; no dropouts |
| Freeze loop periods (autocorrelation, corr 1.000) | 480 / 240 / 120 ms = 1/4, 1/8, 1/16 of a bar at 125 BPM, exact |
| Freeze clicks | none. At entry, at the loop point and at exit, for all three Lengths, and in a 5x 100 ms stutter, the largest sample-to-sample step stayed at 0.76x to 1.17x of plain play's own (reference 6,864 to 8,327). No 20 ms window of the stutter region went above 1.3x |
| Soak | 10 min, a 1 s freeze every 30 s, at 141.5 BPM (the maintainer had changed the tempo by hand): 978,845 blocks, 0 underrun, 0 fault, 0 slip, 0 hwfault, guard shed 0; `crash` empty |
| Way back | `--update` of `o3os_1.0.0-pads.1.ptf` (CRC `22BD52A5`), about 46 s, start state restored |

Notes:
- The Length key cycles (now + 1) mod 3 and keeps its value until a reboot. An earlier, overlapping attempt left Length at 1/4, so the measured order was 1/4, 1/8, 1/16. That is correct behaviour.
- `key <b> hold <ms>` acknowledges at once and the hold runs in the firmware. A script must sleep the hold's own length.
- The first soak was paused while the maintainer used the unit by hand, then run again in full.

## What this verifies

- R6, the beat freeze, works on the unit: exact loop lengths, no clicks, no CPU peak above plain play, clean over a soak.
- The M3b sequencer engine (f3c08e6) plays the existing patterns as before.

Ratchets, conditions, FILL and the slew have no screen control in this image, so they are not exercised on the unit yet. They come with the ui slices.
